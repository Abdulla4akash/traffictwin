## 1. Canonical lifecycle

```
offered
 ├─ gate_rejected (terminal, admission gate)
 ├─ capacity_rejected (terminal, waiting-room full)
 └─ admitted ── forwarded (path event: ingress RSU → execution RSU)
        └─ started → compute_completed ─┬─ returned → deadline_success
                                        └─ dropped
```

- **offered** — task generated by vehicle workload, presented to infrastructure [SOURCE-DERIVED FACT per research audit §7 common reporting contract; IMPLEMENTATION-VERIFIED FACT if evaluator counts offered].
- **gate_rejected / capacity_rejected** — terminal rejections outside any RSU queue, no retry/fallback/re-forwarding [SOURCE-DERIVED FACT S-007; SOURCE-DERIVED FACT S-035 fail-fast].
- **admitted** — entered waiting-room/queue subject to per-RSU admission/in-flight ceiling [SOURCE-DERIVED FACT S-007].
- **forwarded** — admitted V2I task whose execution RSU differs from ingress RSU; path event not a separate accounting class [RESEARCH-EVIDENCE FACT E2d ingress_to_execution matrix; INFERENCE that forwarded ⊆ admitted].
- **started / compute_completed / returned / dropped / deadline_success** — physical progression distinctions defined in contract [SOURCE-DERIVED FACT S-007 separation requirement; INFERENCE for unavailable sub-fields in current evaluator].

Partial order enforced: offered → {admitted, gate_rejected, capacity_rejected}; admitted → {forwarded, started}; started → compute_completed → {returned, dropped}; returned → deadline_success. Validator checks `offered == admitted + gate_rejected + capacity_rejected`, `admitted >= forwarded`, `admitted >= started >= compute_completed >= returned >= deadline_success`, `compute_completed == returned + dropped`.
